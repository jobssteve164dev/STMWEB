# STMWEB 模块化固件组合标准

## 1. 目标

STMWEB 要建立的不是“选择一块板卡，再编译一整套预制工程”的固件生成器，而是一套可以像积木一样组合硬件能力的标准。

用户只描述自己的硬件并选择“希望它做什么”。平台把目标解析为能力积木，自动寻找当前硬件上的实现，完成资源分配、安全校验、代码组合、隔离构建、最终制品验证和运行态能力声明。用户不需要理解启动文件、链接脚本、引脚复用、定时器、DMA、Bootloader 或具体传输协议。

标准化的对象不是固定二进制，也不是某块板卡自己的模块菜单，而是积木之间稳定的插接面：

- 能力和端口如何声明；
- 组件需要与提供什么；
- 硬件资源如何描述和绑定；
- 生命周期与安全行为如何统一；
- 组合结果如何解析、构建、验证和追溯；
- 设备如何声明最终实际具备的能力。

只有同一个能力积木无需修改业务实现，就能通过不同硬件适配器在两种真实硬件上完成生成、烧录、启动、能力识别和调试闭环，才能证明这套标准跨越了硬件差异。

## 2. 用户动作与产品心智

普通用户完成一次固件创作只需要：

1. 选择已有板卡，或在引导下描述自己的硬件；
2. 选择希望设备具备的能力，例如运动、避障、灯光、电池提醒、遥测或蓝牙控制；
3. 填写少量与作品目标直接有关的参数；
4. 查看平台给出的可行性结论和自动补齐结果；
5. 点击生成并烧录；
6. 连接设备后直接使用与所选能力对应的控制和数据界面。

平台内部的 MCU Pack、驱动、引脚绑定、资源分配、协议版本和构建制品不构成普通用户的学习前提。高级用户可以展开组合图、资源图和构建详情，但这些信息不能成为完成主动作的必选项。

界面中的积木使用用户目标语言，例如“双轮运动”“距离感知”和“电池提醒”，不直接使用 `PWM`、`TIM3`、`ADC1_IN4` 等工程对象作为主选项。

## 3. 总体结构

```text
用户目标与参数
      │
      ▼
能力积木与方案模板
      │  声明 provides / requires / constraints
      ▼
组合解析器与资源求解器
      │  选择实现、绑定端口、分配资源、验证约束
      ▼
不可变解析后组合图
      │
      ├── 平台基座
      ├── 可复用能力积木
      ├── 器件驱动包
      ├── MCU Pack
      ├── Board Pack
      └── Transport Pack
      │
      ▼
生成绑定代码与构建计划
      │
      ▼
隔离构建 → 最终制品验证 → 标准固件包
      │
      ▼
烧录 → 运行态能力发现 → 动态调试界面
```

同一条链路只有一份组合真相：服务端生成并保存的不可变解析后组合图。前端、Runner、固件清单、服务端登记和设备运行态都必须消费或验证这份图，不能根据界面文字、文件名或本地默认值重新猜测组合结果。

## 4. 万变不离其宗的基座

平台基座定义所有标准固件都必须遵守的稳定语义和接口：

- 设备、硬件适配和固件身份；
- 配置读取、校验和持久化；
- 命令、状态、事件与遥测通道；
- 能力发现与接口版本协商；
- `init / start / stop / safeStop / recover` 生命周期；
- 故障、健康和启动确认；
- 完整性校验；
- 升级、重启和恢复入口；
- 资源绑定结果的初始化；
- 调试台与固件之间的标准交互协议。

基座稳定的是合同和行为，不是跨 MCU 复用同一个二进制。复位、Flash 写入、时钟、中断和持久存储等底层动作仍由对应适配实现。

基座不得包含某块板卡的引脚号、某种传感器的寄存器、某个产品的控制算法或 DOT 专属内存布局。

## 5. 可组合对象

### 5.1 能力积木

能力积木表达用户能够理解和使用的功能，例如差速运动、姿态稳定、距离感知、电池状态、灯光反馈、参数调节和实时遥测。

能力积木只依赖标准端口，不直接依赖具体板卡引脚或某份板卡工程。例如“差速运动”需要两个电机执行器和运动状态输出，但不应知道 PWM 位于哪个定时器。

### 5.2 方案模板

方案模板是面向入门用户的一组能力选择和默认参数，例如“蓝牙遥控小车”或“桌面环境监测器”。模板只能展开为标准能力积木，不能形成绕开组合协议的另一套构建路径。用户可以从模板开始，再添加、移除或调整能力。

### 5.3 器件驱动包

器件驱动包实现可复用硬件器件，例如传感器、电机驱动芯片或显示屏。它通过标准端口申请总线、输入输出和中断资源，并向上提供传感、执行或存储能力。

例如，一个惯性传感器驱动可以声明“需要一条 I²C 总线和一个可选中断输入，提供三轴加速度与角速度”，而不知道自己最终安装在哪块板卡上。

## 6. 硬件适配器边界

硬件差异不能继续集中在一个包含 MCU、板卡、功能和传输的单体适配器中。正式模型分为三类硬件 Pack，器件驱动作为能力与板卡之间的可复用实现。

### 6.1 MCU Pack

MCU Pack 负责芯片级事实与实现：

- 启动、时钟、复位和中断模型；
- Flash、RAM、持久存储和链接能力；
- GPIO、ADC、PWM、定时器、UART、I²C、SPI、CAN、USB、DMA 等资源类型；
- 引脚复用、通道、优先级和独占约束；
- 芯片识别与 Flash 算法；
- 工具链、编译参数和目标验证；
- 低功耗与芯片级安全动作。

### 6.2 Board Pack

Board Pack 负责板卡级事实：

- 板卡身份和修订版本；
- MCU 型号及实际容量；
- 引脚、电源、时钟和外围连接；
- 板载器件及其总线地址；
- 已占用、保留和可供组合的资源；
- 使能、复位、方向和电气限制；
- 上电、断电、停止和故障时的安全状态。

Board Pack 可以为板载器件提供默认绑定，但不能重新定义能力积木的公共接口，也不能复制器件的通用驱动逻辑。

### 6.3 Transport Pack

Transport Pack 负责连接和升级的具体实现：

- SWD、UART、BLE GATT、USB、局域网等传输；
- 握手、分块、确认、重试和重连；
- MTU、吞吐、缓冲区和时序要求；
- 进入升级、安全停止、重启和结果确认；
- 中断后的恢复行为。

SWD 是已适配 STM32 目标的长期有线烧录能力。无线、USB 或网络升级只在硬件、运行时和制品共同满足合同后出现。

## 7. 标准组件合同

每个能力积木、器件驱动和传输实现都必须提供版本化组件清单。结构可以演进，但语义至少包含：

```json
{
  "schemaVersion": 1,
  "id": "capability.motion.differential-drive",
  "version": "1.0.0",
  "kind": "capability",
  "provides": [
    { "port": "motion.velocity-control", "version": "1" },
    { "port": "state.motion", "version": "1" }
  ],
  "requires": [
    { "port": "actuator.motor", "version": "1", "count": 2 }
  ],
  "configuration": {
    "schema": "schemas/differential-drive.schema.json"
  },
  "resources": {
    "flashBytesMaximum": 12288,
    "ramBytesMaximum": 4096,
    "updateRateHzMinimum": 200
  },
  "lifecycle": ["init", "start", "stop", "safeStop"],
  "safety": {
    "safeStopRequired": true
  },
  "build": {
    "sources": ["src/*.c"],
    "publicIncludes": ["include"]
  }
}
```

合同必须回答：

- 组件提供哪些带版本的标准端口；
- 组件需要哪些端口、数量和可选性；
- 哪些参数由用户配置，单位和合法范围是什么；
- 需要多少 Flash、RAM、缓冲区和实时预算；
- 如何初始化、运行、停止和恢复；
- 发生故障时如何进入安全状态；
- 哪些源码、生成步骤和编译定义真实参与构建；
- 用什么测试证明该实现符合接口合同。

首版采用源码级接口、静态链接和生成绑定代码，不要求建立跨工具链的二进制插件 ABI。组件未被选中且未被依赖时，其业务源码不得进入最终构建。

## 8. 标准端口与资源模型

端口描述能力之间的语义连接，而不是具体函数名或引脚号。端口至少包含稳定 ID 与主版本、方向、数据结构、单位、范围、交互方式、数量、共享规则、时序要求和失败行为。

例如 `sensor.distance@1`、`actuator.motor@1`、`telemetry.stream@1`。主版本不兼容时必须在构建前停止，不能依赖编译器偶然通过。

资源模型描述当前硬件可以提供什么，以及组件需要占用什么。首版至少覆盖：

- 引脚及复用功能；
- ADC、PWM、定时器和捕获比较通道；
- UART、I²C、SPI 和 CAN 总线；
- DMA 通道；
- 中断线与优先级；
- Flash、RAM、栈和持久存储；
- 时钟、带宽和周期预算；
- 电压、方向、上拉和板级安全限制。

资源声明需要区分独占、可共享、按地址共享和有容量上限的资源。只通过组件 ID 写死 `conflicts` 可以作为补充规则，不能代替资源求解。

## 9. 组合解析与约束求解

用户选择能力后，服务端必须执行确定性的组合解析：

1. 展开方案模板；
2. 加入平台必需基座；
3. 递归解析能力端口依赖；
4. 为每个端口选择满足版本与约束的实现；
5. 根据 Board Pack 绑定板载器件；
6. 根据 MCU Pack 分配引脚、总线、定时器、DMA、中断和存储；
7. 检查电气、容量、时序、安全和版本约束；
8. 确定 Transport Pack 与最终可用烧录方式；
9. 生成不可变解析后组合图；
10. 由组合图生成绑定代码和构建计划。

同一输入、同一目录版本和同一求解器版本必须得到同一解析结果。存在多个同等实现时，平台使用可追溯的默认策略；只有差异会改变用户目标、成本、风险或结果时，才要求用户选择。

解析失败必须在启动构建前发生，并使用用户能够行动的语言。例如：

> 电机控制和舵机同时需要当前板卡唯一的高频定时器。请移除其中一项，或选择具有更多定时器的板卡。

普通用户不应只看到 `TIM3 allocation conflict`、链接器错误或组件内部 ID。

## 10. 不可变解析后组合图

硬件项目保存用户意图和参数；每次构建创建一份不可变解析后组合图。后续编辑项目、更新组件目录或发布新适配器，不能改变已经排队、执行或完成的构建。

组合图至少记录：

- 用户选择的能力和参数；
- 平台自动加入的基座与依赖；
- 每个标准端口最终绑定的实现；
- 每项硬件资源的分配结果；
- MCU、板卡、器件、传输和组件的精确版本；
- 构建输入、生成配置和工具链身份；
- 可用烧录方式和制品角色；
- 求解器版本及每项自动选择的理由；
- 安全链和最终验证要求。

Runner 只消费服务端签发的组合图和构建输入，不重新求解。最终固件清单必须携带组合图身份及解析结果摘要；服务端登记固件包时，再次校验任务、组合图、最终字节和清单一致。

## 11. 生成、验证与运行态闭环

```text
描述硬件与用户目标
→ 解析能力和实现
→ 分配资源并验证约束
→ 冻结组合图
→ 生成绑定代码与构建计划
→ 隔离构建
→ 检查最终 ELF / HEX / BIN
→ 校验组合身份、布局、容量、向量和摘要
→ 生成标准固件包
→ 烧录并确认启动
→ 设备回报实际能力
→ 调试台按实际能力呈现操作
```

验证对象必须是最终生成物，而不只是组件清单或源模板。至少验证：

- 未选择且未被依赖的模块没有进入最终链接结果；
- 所有必需端口都有且只有合法实现；
- 最终资源占用与求解结果一致；
- Flash、RAM、向量和分区没有越界；
- 安全停止链与恢复入口真实存在；
- 固件内嵌的组合身份与构建任务一致；
- 设备启动后声明的能力与固件清单一致；
- 页面只显示设备实际具备且当前可用的动作。

## 12. 前台呈现

“创建固件”主路径只展示：

- 我的硬件；
- 我想实现的能力；
- 与作品相关的参数；
- 平台自动补齐的简短摘要；
- 是否可以生成，以及需要用户处理的问题；
- 将获得的完整固件、应用固件和可用烧录方式。

资源图、绑定明细、组件版本、ELF、MAP、链接脚本、日志和固件清单进入高级详情。组件化是平台吸收复杂度的方式，不应把最终体验变成面向工程人员的节点编辑器。

## 13. 当前实现与纠偏边界

### Observed in code

当前 DOT 纵向切片已经把组合协议推进到版本 2：组件合同能够声明标准端口、端口依赖、硬件资源需求和构建特征；服务端解析依赖、绑定实现与板卡资源，生成带内容摘要的不可变组合图。Runner 只接受版本 2 组合图，把同一份图交给 CMake；原始固件清单在构建阶段写入该组合图，服务端登记时重新计算并核对任务、适配器、清单、嵌入固件的组合图和实际制品字节。

蓝牙应用升级是首个真实可裁剪组件。选择蓝牙时，组合器把它绑定到 DOT 的 USART3 并产生 `dot.bluetooth-update` 构建特征，CMake 才编译升级桥；仅选择 SWD 时该源码不会进入最终 ELF，应用制品也不会声明蓝牙烧录方式。两种组合均已使用同一 ARM GNU 工具链生成并校验最终 ELF、HEX、BIN 和原始固件清单。

当前运动、电池、参数和遥测仍来自耦合的 DOT 旧工程，还没有成为独立源码包；MCU、Board 与器件实现也尚未从目录结构上拆开。因此这一版证明了组合合同到真实构建的首个软件闭环，不代表完整能力积木迁移或跨硬件标准已经成立。

### 生产闭环证据（2026-08-27）

协议版本 2 已通过正式 Runner `firmware-compilation v0.3.7` 的发布字节校验，并安装到生产编译目标。随后从同一源码和同一 DOT 硬件适配器发起两次全新构建，均完成 Runner 构建、服务端登记、最终制品校验和固件包验证，每个包包含 12 项制品：

| 用户选择 | 生产构建 | 最终组合结果 | 最终 ELF 证据 |
| --- | --- | --- | --- |
| 仅 SWD | `c819c9d6-0b47-43a1-a75b-b539e59d87bd` | 运行传输仅 `swd`；无额外构建特征；无 UART 资源绑定；组合摘要 `537282fd17a4abd9dfe63a7868beb3e9957b6d143901e77c58fda4ddbab45be5` | 不包含 `legacy_communication` |
| SWD + 蓝牙 | `fe90180b-1fb3-4fce-9584-b4d6faa94edc` | 增加 `bluetooth-uart`、`dot.bluetooth-update`，并将 `connection.bluetooth` 绑定到 `board.usart3`；组合摘要 `2d6a786536c3e08c77d0f85eb6ea28dadd90adf4659828886f52a4a8bad69319` | 包含 `legacy_communication` |

这组证据确认：用户选择已经真实改变依赖解析、硬件资源绑定、编译输入、应用固件可用烧录方式和最终链接结果，不再只是改变页面标签或清单元数据。

生产闭环同时确立三项一致性规则：

- 组合图写入数据库或经过对象序列化后，摘要和相等性判断必须使用递归规范化 JSON，不能依赖属性顺序；
- 固件内嵌组合图必须在语义校验后继续按构建时原始字节验真，不能用校验器重排后的对象代替最终生成物；
- 构建任务一旦进入成功、失败或取消终态，迟到事件不得逆转终态。

以上仅完成 DOT 上“连接积木可裁剪”的第一条生产纵向切片。运动、电池、参数、遥测的源码独立化，以及第二种真实硬件上的无修改复用，仍按后续验收标准推进。

### 必须纠正

- 模块目录从“每块板卡自己的功能菜单”改为可复用组件目录；
- DOT 单体适配器拆分为 MCU、Board、器件与 Transport Pack；
- 功能模块从标签升级为包含代码和标准端口的能力积木；
- 继续把运动、电池、参数和遥测接入已建立的端口、资源与构建特征合同；
- 将首版 UART 资源绑定扩展到引脚、定时器、DMA、中断、Flash 和 RAM 约束；
- 让所有能力选择都真实改变最终构建和运行态能力；
- 设备能力发现必须来自最终固件，而不是页面根据板卡型号预设。

现有硬件项目、Runner 租约、固件包、稳定版发布、SWD 与无线烧录路径继续保留并服务新组合协议，不另建一套平行用户流程。

## 14. 落地顺序

### 14.1 合同基线

1. 定义组件、端口、资源、生命周期、安全和构建输入合同；
2. 定义 MCU、Board、器件与 Transport Pack 合同；
3. 定义不可变解析后组合图及固件内嵌身份；
4. 用 DOT 当前完整构建作为行为不变的回归基线。

### 14.2 DOT 迁移切片

1. 拆出 STM32F103 MCU Pack；
2. 拆出 DOT V1 Board Pack；
3. 拆出当前使用的传感器、电机、电池和蓝牙器件实现；
4. 把运动、电池、参数和遥测改为真实能力积木；
5. 让选择结果控制源码、绑定生成和运行态能力注册；
6. 保持当前 SWD、蓝牙升级、固件包和工作区流程不变；
7. 使用真实 DOT 回归烧录、启动、能力发现和版本更新。

### 14.3 第二种硬件验收

第二种真实硬件必须复用至少一个未经业务代码修改的能力积木，并完成：

- 使用新的 MCU、Board、器件或 Transport Pack 完成绑定；
- 经同一解析器、组合图、Runner 和固件包流程生成；
- 使用真实硬件完成烧录和启动；
- 设备回报与组合图一致的实际能力；
- 调试台自动呈现对应动作；
- 完成至少一次固件更新；
- 没有无线能力时，仅通过长期 SWD 也能完成闭环。

## 15. 完成标准

### 15.1 软件组合闭环

以下条件全部成立，才能声明模块化组合的软件闭环完成：

1. 能力积木、标准端口和四类适配对象拥有独立版本化合同；
2. 组合器能够解析依赖、选择实现并分配首版硬件资源；
3. 每次构建生成不可变解析后组合图；
4. 模块选择真实改变构建输入和运行态能力；
5. Runner、最终固件清单和服务端登记验证同一组合身份；
6. 失败在构建前以用户可行动的方式说明；
7. 普通用户不需要理解适配器和硬件资源即可完成生成；
8. DOT 现有真实烧录和升级行为没有回归。

### 15.2 跨硬件标准成立

只有第二种真实硬件通过第 14.3 节验收，才能声明跨硬件组合标准成立。增加第二份板卡专属模块目录、复制能力代码或复制用户流程，不算跨硬件复用。

## 16. 非目标与待确认项

首版不追求：

- 任意来源代码不经适配即可组合；
- 在 MCU 上动态加载二进制插件；
- 让普通用户手工搭建驱动与引脚节点图；
- 一次覆盖全部 STM32、RTOS、无线协议和器件生态；
- 用一个超级 HAL 隐藏所有芯片差异；
- 在组合合同尚未成立前建立开放组件市场。

仍需后续确认：

1. 首版标准端口目录及版本规则；
2. 首版资源求解覆盖范围和确定性选择策略；
3. 组件包的可信来源、签名与发布权限；
4. 用户自定义代码接入能力积木的最小开发接口；
5. 用于跨硬件验收的第二种真实板卡；
6. 第一批面向普通用户提供的方案模板。

这些选择影响实现顺序，但不改变核心判断：平台必须通过稳定插接合同、自动适配和可验证组合吸收技术差异，用户只围绕自己的硬件目标和想象力行动。
