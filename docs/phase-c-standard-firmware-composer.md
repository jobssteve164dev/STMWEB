# 第三阶段：标准固件组装器设计

> 本文保留第三阶段现有实现切片与交付背景。模块化架构、组件插接合同、适配器边界、组合求解和跨硬件完成标准，以 [STMWEB 模块化固件组合标准](modular-firmware-composition-standard.md) 为准。本文中的“板卡模块目录”仅作为现有 DOT 切片的迁移起点，不再代表目标架构。

## 1. 目标

第三阶段把当前“选择硬件项目、上传源码、发送 Runner 编译”的末端构建入口，升级为用户可以直接组装标准固件的完整产品路径。

用户只围绕自己的硬件和功能做选择。平台负责自动补齐启动、设备身份、调试、升级、恢复、链接布局、构建参数和最终校验，并把不可变构建计划发送给用户授权的隔离 Runner。第二种真实硬件用于验收这条路径没有写死 DOT，不是第三阶段的全部产品内容。

## 2. 用户动作

用户按以下顺序完成一次标准固件生成：

1. 为固件命名并选择经过验证的板卡模板；
2. 从当前硬件支持的功能模块中选择需要的能力；
3. 查看平台自动加入的基础能力与可用连接方式；
4. 创建硬件项目，保存一份可继续使用的固件配置；
5. 选择源码包和在线编译算力；
6. 点击生成标准固件；
7. 查看生成和校验状态；
8. 获得“完整固件”和“应用固件”，随后直接发布或烧录。

普通用户不需要选择 Bootloader 文件、链接脚本、应用地址、协议版本、编译器中间文件或固件拼接方式。

## 3. 模块分层

当前 DOT 迁移切片暂时从单体硬件适配器发布版本化模块目录；正式架构中的能力积木与器件驱动应进入独立可复用组件目录，并通过 MCU、Board 与 Transport Pack 完成硬件绑定。用户选择仍按以下三层呈现。

### 3.1 平台基础模块

平台基础模块始终自动装配、默认不可移除，但可以在生成预览中查看。首版至少包括：

- 启动与恢复；
- 设备身份；
- 能力发现与调试协议；
- 完整性校验；
- 安全停止与重启确认。

这些模块是形成“标准固件”的必要条件，不能让用户通过错误组合生成无法识别、无法恢复或无法安全升级的固件。

### 3.2 功能模块

功能模块用用户语言表达硬件能力，例如电机控制、电池状态、参数调节和实时遥测。用户可以选择；平台根据板卡目标实时给出可用性，并自动补齐模块依赖。

模块合同至少包含稳定 ID、版本、名称、说明、标准端口、资源需求、生命周期、安全行为、真实构建输入和依赖关系。首版不向用户暴露源文件列表、编译宏或内部组件名称。

### 3.3 连接模块

SWD 是每个已适配 STM32 目标的长期基础连接，平台自动加入。蓝牙、USB 或网络升级只有在硬件适配、设备侧运行时和固件制品共同支持时才出现。

用户选择的是“需要哪些连接能力”，平台决定 Bootloader、传输适配器、协议和烧录制品如何组合。

## 4. 配置与构建真相

硬件项目保存当前固件配置；每次创建构建时，服务端必须把配置解析为不可变快照并写入构建任务。后续编辑硬件项目不能改变已经排队、执行或完成的构建。

不可变解析后组合图至少包含：

```json
{
  "schemaVersion": 2,
  "foundationModules": ["..."],
  "capabilityModules": ["..."],
  "connectionModules": ["..."],
  "runtimeTransports": ["..."],
  "components": ["..."],
  "portBindings": ["..."],
  "resourceBindings": ["..."],
  "buildFeatures": ["..."],
  "compositionSha256": "..."
}
```

服务端只接受已登记的组件和适配实现；必需基座由服务端重新补齐，未知组件、端口缺失、目标不支持、资源不足和冲突组合必须在创建项目或构建前拒绝。前端校验只用于即时反馈，不能承担合同边界。

Runner 租约必须携带已经解析的组合图和适配器构建目录。Runner 不能根据界面文字、文件名或本地默认值重新猜测配置，也不能重新求解。构建命令必须消费该组合图，并把同一份组合信息写入最终固件和权威固件清单。

服务端登记固件包时，必须再次验证清单中的组合信息与构建任务快照一致。

## 5. 前台结构

“标准固件生成”使用渐进披露，不把全部工程对象平铺给用户。

### 5.1 固件配置

- 板卡模板：决定受支持 MCU、容量和适配版本；
- 功能模块：以可选择卡片展示；
- 平台自动装配：以简短摘要展示，不提供破坏性开关；
- 连接能力：显示平台根据硬件自动确定的长期 SWD 和可选无线方式；
- 生成预览：显示已选能力、可用烧录方式和将产生的两类正式固件。

### 5.2 构建

用户选择硬件项目、源码包和在线 Runner 后发起构建。页面显示生成状态和可行动错误，不要求用户阅读编译器日志才能理解主路径结果。

### 5.3 结果

构建成功后，主操作区只显示：

- 下载完整固件；
- 下载应用固件；
- 发布稳定版。

ELF、普通 HEX/BIN、MAP、Bootloader 中间文件、日志和固件清单属于高级构建制品，统一收进可展开的“构建详情”，并显示真实文件名、类型和大小。按钮不得只显示重复的扩展名。

## 6. 第三阶段交付边界

### 6.1 软件闭环

满足以下条件时，可声明第三阶段的软件组装闭环成立：

1. 模块目录由版本化硬件适配器驱动，不写死在页面；
2. 用户可创建包含功能选择的硬件项目；
3. 服务端校验并保存配置，构建任务形成不可变快照；
4. Runner 消费快照并把组合信息写入最终固件与固件清单；
5. 服务端依据快照和实际字节复验后登记标准固件包；
6. 页面只突出完整固件和应用固件，高级制品按需展开；
7. 桌面与 375 px 视口均能完成配置和下载动作。

### 6.2 跨硬件验收

只有第二种真实 STM32 板卡或新的真实连接适配完成以下闭环后，才能声明阶段 C 全部完成：

- 复用同一模块目录、项目配置、构建任务、固件包和前台流程；
- 新增内容保持在 MCU、板卡或传输适配层，不复制固件管理页面；
- 使用正式编译环境生成并校验真实制品；
- 使用真实硬件完成烧录、启动、能力识别和至少一次版本更新；
- 若硬件没有无线能力，能够只通过长期 SWD 完成完整闭环。

未提供第二种实物硬件和验收记录时，只能声明软件闭环完成，不能宣称跨硬件通用。

## 7. 首个实现切片

首个切片使用已经实物验证的 DOT V1，开放当前已经成立的电机控制、电池状态、参数调节和实时遥测模块。平台自动装配启动恢复、设备身份、调试与完整性能力，并根据 DOT 适配声明提供 SWD 和蓝牙应用升级。

这个切片的目的，是先证明用户选择、服务端解析、不可变快照、Runner 消费、清单复验和最终结果展示属于同一条真实链路；它不作为第二种硬件证据。
