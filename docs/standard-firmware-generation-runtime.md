# STMWEB 标准固件生成运行时设计

## 1. 产品目标

STMWEB 的核心价值不是保存固件文件，也不是把串口工具、DAP 工具和蓝牙工具搬进同一个网页。平台要让用户把注意力留在硬件功能、实时反馈和创造过程本身，并吸收编译、链接、调试、探针、烧录、升级与恢复工具之间的切换成本。

为此，STMWEB 建立一套标准化且高度自动化的固件生成运行时：平台把用户的硬件描述、连接选择和应用代码转换为一套可识别、可调试、可烧录、可恢复、可追溯的标准固件版本。用户不需要拥有 STMWEB 项目仓库的发布权限，也不需要理解平台内部使用了哪一种工具链或传输协议。

“标准固件”不是适用于所有硬件的固定二进制。标准化发生在用户动作、生成合同、设备运行时、制品描述和安全校验上；MCU、板卡与传输差异由适配器吸收。

## 2. 已确认的产品决策

1. 固件生成运行时是产品主线，文件上传、Runner、制品管理和烧录卡片均服务于这条主线。
2. SWD 是稳定、通用、长期可用的有线烧录路径，不是仅供第一次连接使用的临时工具。
3. 无线烧录是硬件支持且完成适配时出现的另一条长期路径；没有无线能力的硬件使用 SWD 属于完整、正常的产品体验。
4. 首次安装、日常更新、恢复设备和维护 Bootloader 是烧录任务，不应拆成要求用户理解多套工具的工程入口。
5. 每个用户拥有自己的硬件工作区和固件版本。平台根据登录身份、工作区权限、目标设备和制品兼容性决定哪些固件可以显示和烧录。
6. 平台应提供 Bootloader、链接布局、设备侧运行时、接入代码、构建模板和验证工具；用户负责产品特有的硬件驱动与业务逻辑，不从零设计平台烧录协议。
7. DOT 是第一套真实参考适配，不是长期写死在产品界面和通用数据模型中的特殊设备。

## 3. 用户动作模型

普通用户只需要完成以下动作：

1. 创建硬件项目。
2. 选择已有板卡，或描述 MCU、板卡版本、外设和可用连接方式。
3. 连接自己的代码仓库、提交源码包，或导入已有构建产物。
4. 选择需要的调试能力和烧录方式。
5. 点击生成固件。
6. 查看平台给出的明确校验结果。
7. 通过 SWD 或设备支持的无线方式烧录。
8. 设备重启后直接进入调试台，继续观察、控制和记录。

用户不需要在主路径中填写应用起始地址、手工选择链接脚本、拼接 Bootloader 与应用、计算校验值或判断应该使用哪种烧录程序。这些信息可以在高级详情中查看，但不能成为完成动作的前置知识。

## 4. 总体结构

```text
硬件描述 + 用户应用代码 + 连接与能力选择
                       │
                       ▼
              平台侧固件生成运行时
  目标适配 → 布局生成 → 运行时组合 → 隔离构建 → 制品校验
                       │
                       ▼
 完整 SWD 镜像 + 应用镜像 + 可选无线镜像 + 固件清单
                       │
                       ▼
       工作区固件版本 → 兼容性匹配 → 烧录与调试
                       │
                       ▼
              设备侧标准运行时
   设备身份、能力发现、调试协议、升级入口、恢复与状态
```

生成运行时包含两个互相约束的部分：平台侧生成运行时负责产生和验证固件；设备侧标准运行时负责让生成后的固件持续遵守设备身份、调试和升级合同。

## 5. 平台侧生成运行时

平台侧运行时负责：

- 根据硬件描述选择受支持的 MCU、板卡和传输适配器；
- 计算 Flash、RAM、Bootloader、应用和元数据布局；
- 生成启动代码、链接脚本、板级配置和运行时配置；
- 把调试、设备身份、能力发现、升级入口和安全停止能力组合进应用；
- 在用户授权的隔离 Runner 中使用固定工具链构建；
- 生成 ELF、HEX、BIN、MAP、体积报告、日志和标准固件清单；
- 对最终生成物而非只对模板执行地址、容量、向量、摘要和兼容性检查；
- 将验证通过的版本登记到当前用户工作区，并供烧录卡片直接消费。

平台不应在自己的公共服务中直接执行任意不可信源码。用户源码可以来自用户自己的仓库、一次性源码包或本地工程；正式构建在绑定当前工作区的隔离 Runner 中完成。用户不需要把源码发布到 STMWEB 仓库。

## 6. 设备侧标准运行时

设备侧运行时应以小型、可裁剪组件提供：

- 稳定设备身份、硬件适配 ID 和板卡版本；
- MCU、Flash、内存布局和 Bootloader 协议信息；
- 固件版本、构建来源和应用有效状态；
- 调试能力描述、运行状态、遥测、控制和事件协议；
- 安全停止、进入升级、重启和启动确认；
- 有线或无线传输适配器与统一升级状态；
- 传输中断后的恢复入口；
- 完整性校验以及后续签名、防回滚能力。

运行时只统一平台合同，不替用户生成产品特有的电机算法、传感器驱动和业务功能。硬件差异留在板级适配与用户代码中，但不得迫使普通用户理解平台内部工具差异。

## 7. 适配器模型

生成运行时通过三类适配器扩展，而不是复制一套新的页面：

| 适配器 | 负责内容 | 示例 |
| --- | --- | --- |
| MCU 适配器 | 启动、内存、Flash 算法、工具链和目标识别 | STM32F103 中容量系列 |
| 板卡适配器 | 引脚、时钟、外设、板卡修订和安全动作 | DOT V1 |
| 传输适配器 | 连接、握手、分块、重试和重启确认 | CMSIS-DAP、UART 蓝牙透传 |

“通用 SWD”指统一的产品动作和制品合同。底层仍必须为受支持的 MCU 提供正确的 Flash 算法，并在擦除前读取真实芯片信息。平台不得用 DOT 的固定算法或仅凭用户选择冒充支持其他芯片。

无线同样不是单一协议。UART 蓝牙透传、BLE GATT、USB DFU 和网络 OTA 可以共享升级状态与制品合同，但各自需要经过验证的传输适配器。

## 8. 工作区与固件版本

内部数据关系为：

```text
工作区
└── 硬件项目
    ├── 硬件适配版本
    ├── 设备
    └── 固件版本
        ├── 生成输入与运行时版本
        ├── 兼容性清单
        ├── 完整 SWD 镜像
        ├── 应用镜像
        └── 可选无线升级镜像
```

前台不需要向普通用户展示全部内部对象。用户主要看到“硬件项目、固件版本、生成状态、可用烧录方式和验证结果”。

固件版本建议使用以下状态：

- `draft`：配置或上传尚未完成；
- `validating`：平台正在验证生成输入或制品；
- `verified`：结构与兼容性检查通过，可以试烧；
- `stable`：工作区明确选定的稳定版本；
- `retired`：保留历史和审计，但不再作为默认烧录选择。

上传文件不应因为扩展名正确就直接进入正式烧录列表。烧录卡片默认只读取当前工作区内、用户有权访问、目标硬件匹配且状态允许烧录的版本。

## 9. 标准固件包合同

一个固件版本可以包含多份制品，但只有一份权威清单。下列结构表达设计边界，不代表已经冻结的 API Schema：

```json
{
  "schemaVersion": 1,
  "hardware": {
    "profileId": "vendor.board",
    "revision": "1",
    "mcuFamily": "stm32f103",
    "deviceIds": [1040],
    "flashBytes": 65536
  },
  "runtime": {
    "version": "1",
    "debugProtocol": "1",
    "bootProtocol": "1",
    "transports": ["swd", "bluetooth-uart"]
  },
  "memory": {
    "applicationBase": 134221824,
    "applicationLimit": 134282240
  },
  "artifacts": [
    {
      "role": "complete-image",
      "format": "ihex",
      "flashMethods": ["swd"],
      "size": 0,
      "sha256": "..."
    },
    {
      "role": "application",
      "format": "bin",
      "flashMethods": ["swd", "bluetooth-uart"],
      "size": 0,
      "sha256": "..."
    }
  ]
}
```

同一应用 BIN 同时兼容 SWD 和无线时只保存一份，由清单声明两种方式。完整镜像、应用镜像和 Bootloader 镜像是制品角色，不是三套相互割裂的用户工作流。

## 10. 固件生成与发布流水线

正式流水线为：

```text
描述硬件
→ 校验支持范围
→ 解析用户工程
→ 生成板级配置和内存布局
→ 组合设备侧运行时
→ 隔离构建
→ 检查最终 ELF/HEX/BIN
→ 生成并校验固件清单
→ 登记 verified 版本
→ 用户发布 stable 版本
```

每次生成必须绑定不可变的源码身份、硬件适配版本、运行时版本、工具链身份和构建参数。失败结果需要指出用户可以采取的动作，例如“应用超过目标 Flash 容量”或“当前蓝牙模块不属于已支持传输”，不能只返回编译器日志。

手工导入作为高级兼容入口，必须经过与自动生成物相同的服务端验证。服务端应根据实际接收字节重新计算 SHA-256，不能信任浏览器提交的摘要。

## 11. SWD 有线烧录

“SWD 有线烧录”在固件管理中长期存在，并覆盖：

- 空白芯片完整安装；
- 日常应用更新；
- 没有无线能力的设备长期烧录；
- 无线链路不可用时恢复应用；
- 明确授权后的 Bootloader 维护。

用户选择硬件和固件版本后，平台根据制品角色和设备状态决定执行完整安装、应用更新或恢复。普通动作优先保留无需改写的区域；全片擦除和 Bootloader 更新属于明确提示的恢复或维护动作。

首次接触空白芯片时，SWD 通常只能确认 MCU ID 和 Flash 容量，无法从芯片自动推断板卡引脚与外围电路。因此用户需要选择硬件项目或板卡模板，平台负责在任何擦除前验证可读的芯片事实。平台固件安装后，设备再通过硬件适配 ID 消除后续手工匹配。

## 12. 可选无线烧录

只有硬件描述、设备侧运行时和固件版本共同声明兼容无线传输时，页面才显示对应无线烧录动作。无线烧录不得取代 SWD，也不得让无无线硬件呈现为能力残缺。

无线升级应满足：

- 不覆盖恢复 Bootloader；
- 进入升级前执行设备安全停止；
- 根据设备握手匹配硬件适配 ID、MCU、布局和协议版本；
- 在擦除前完成电源与目标检查；
- 分块传输、确认、重试和整包校验；
- 成功后重启并回报新固件身份；
- 中断后仍能重新进入恢复入口。

如果用户导入的应用没有包含与当前硬件适配相符的升级入口，它不能被标记为支持无线烧录。平台不能仅凭文件名或 `.bin` 扩展名推断能力。

## 13. 目标匹配与防误刷

仅匹配 MCU 和 Flash 容量不足以识别一块真实硬件。两个产品可以使用相同芯片和内存布局，但拥有完全不同的电机、传感器和供电设计。

首次 SWD 前至少检查：

- 用户当前选择的硬件项目；
- 探针实际读回的芯片 ID 与 Flash 容量；
- 制品声明的目标与地址范围；
- 擦除和写入区域是否越界。

平台运行时安装后，有线和无线烧录还应检查：

- 硬件适配 ID 与板卡修订；
- Bootloader 和调试协议版本；
- 应用基址、容量与制品角色；
- 固件完整性和发布状态。

任一必需条件不匹配时，在擦除前停止，并用用户能行动的语言说明不匹配对象。

## 14. 权限与数据隔离

工作区是硬件项目、源身份、构建、固件版本、设备和调试记录的归属边界。用户只会读取当前身份有权访问的数据，不需要 STMWEB 仓库权限。

权限最终应按用户动作表达：查看固件、生成固件、上传制品、发布稳定版、烧录设备和管理硬件适配。当前 `owner / editor / viewer` 成员角色可以映射这些动作，但“谁可以发布”和“谁可以烧录”仍需在公共开放前形成正式产品规则。

所有列表、内容下载和烧录制品读取都必须在服务端校验工作区成员关系与资源归属。前端过滤只改善体验，不能承担安全边界。

## 15. 固件设计指导

固件设计指导应嵌入“创建硬件并生成固件”的动作过程，而不是只提供一篇要求用户自行翻译的工程文档。平台应提供：

- 按 MCU、板卡和连接方式生成的接入包；
- 可直接使用的 Bootloader、链接脚本和运行时配置；
- 用户代码需要实现或映射的少量稳定接口；
- 调试能力和硬件安全动作的配置示例；
- 本地预检与 Runner 构建使用同一套校验器；
- 对每项失败给出文件、配置和修正方向；
- 高级用户可查看的内存图、协议与最终制品详情。

普通用户面对的是“我的板子能做什么、怎样连接、生成结果能否使用”；平台内部的模板、对象模型和适配差异不能成为他们的学习负担。

## 16. 当前实现与目标差距

### Observed in code

- 工作区成员鉴权、固件上传、列表和内容读取已经存在，并以工作区作为查询边界。
- 固件记录已保存硬件适配、内存布局、制品角色、烧录方式和发布状态；用户导入时由服务端根据实际字节重新计算摘要并识别当前已支持的 DOT 制品，未知制品保存为不可烧录草稿。
- DOT V1 已有机器可读的适配器合同；64/128 KiB 的链接布局、Bootloader 布局、目标定义、制品角色和可用烧录方式由该合同驱动，未登记目标会直接拒绝构建。
- 用户可在固件管理中创建绑定适配版本、运行时版本和目标容量的硬件项目，再用自己的 Runner 提交源码包生成固件。
- Runner 会生成包含完整镜像、应用镜像、烧录方式、大小和摘要的标准固件清单；服务端不信任 Runner 的结论，而是重新读取实际制品、计算摘要、检查向量与布局，验证通过后自动登记为同一固件包。
- 固件包可以由用户明确设为稳定版；同一硬件项目只保留一个稳定包。完整固件进入长期 SWD 卡片，应用固件进入蓝牙卡片，两者不再以同一个“稳定版”名称掩盖 Bootloader 边界。
- SWD 已作为长期有线烧录卡片，可从标准清单或工作区选择兼容完整镜像；蓝牙卡片只选择兼容应用镜像。底层当前仍只实现 DOT Bootloader 协议与两种容量布局。
- DOT 适配器已经生成 64/128 KiB 的 Bootloader、重定位应用、完整 SWD HEX 和应用 BIN，并完成真实 64 KiB DOT 的 SWD 与蓝牙烧录验证。

### Inference

阶段 B 的 DOT 纵向切片已经形成：硬件项目、版本化适配合同、Runner 标准包、服务端验真、工作区登记、稳定版发布和烧录消费连成一条路径。它证明了生成运行时的框架能够承载真实硬件，但尚未证明跨硬件通用；该结论必须留给阶段 C 的第二种真实硬件。

## 17. 分阶段落地建议

本节描述依赖顺序，不修改项目路线图状态。

### 阶段 A：固化 DOT 黄金样板

- 已把现有 DOT 构建输入、运行时、布局和输出表达为一份可验证固件清单；
- 已将 SWD 卡片从“首次安装”改为长期有线烧录动作；
- 已让 SWD 和蓝牙卡片按目标、角色、方式和状态读取标准清单或工作区兼容制品；
- 已由服务端重新计算上传内容摘要，缺少目标描述的制品只保存为不可烧录草稿。

### 阶段 B：建立生成运行时

- 已建立硬件项目、适配版本、运行时版本、固件包和完整/应用制品角色；
- 已把 DOT 的 CMake、链接、Bootloader、目标容量与最终生成物验证收敛到版本化适配合同；
- 已由 Runner 生成标准固件包，并由服务端依据实际字节复验后自动登记；
- 已在固件管理中连通创建硬件项目、接入源码、生成、验证、发布稳定版和选择烧录固件；
- 当前交付是 DOT 的首个完整纵向切片，不等于已经完成多 MCU、多板卡或多无线协议支持。

### 阶段 C：建立标准固件组装器并验证第二种硬件

- 按 [第三阶段：标准固件组装器设计](phase-c-standard-firmware-composer.md) 建立用户可视化选择功能模块、平台自动补齐基础模块与连接能力的组装入口；
- 将模块目录、依赖解析、硬件项目配置、不可变构建快照、Runner 构建计划和最终固件清单连成同一条可验证链路；
- 构建结果只突出完整固件和应用固件，编译器中间制品进入高级详情；
- 接入第二个真实 STM32 板卡或第二种真实连接方式；
- 证明新增适配只增加 MCU、板卡或传输适配器，不复制工作台和固件管理流程；
- 证明没有无线能力的硬件可仅通过 SWD 完成生成、烧录、调试和版本闭环。

完成组装器的软件闭环不等于已经证明跨硬件通用。第二种硬件走通之前，不能根据 DOT 单一样本宣称阶段 C 全部完成。

## 18. 尚待确认的产品决策

以下事项尚未由当前讨论完全锁定：

1. 第一批正式开放的 MCU、板卡和无线传输支持矩阵；
2. 源码包上传、用户代码仓库和预编译制品三种输入方式的首版优先级；
3. 公共开放前是否强制固件签名与防回滚；
4. `owner / editor / viewer` 对生成、发布和烧录动作的精确权限；
5. 工作区固件配额、制品保留期限和对象存储迁移时点；
6. 第一个用于证明非 DOT 通用性的真实硬件目标。

这些选择会影响实现顺序，但不改变已经确认的产品原则：平台负责吸收固件生成和烧录工具复杂度，SWD 长期可用，无线按硬件能力出现，用户始终围绕自己的硬件完成动作。

## 19. 验收标准

标准固件生成运行时形成首个可公开验证版本时，至少要证明：

1. 一个没有 STMWEB 仓库权限的新用户可以在自己的工作区创建硬件项目并生成固件；
2. 平台自动产生完整 SWD 镜像、应用镜像、固件清单和可行动的验证结果；
3. 没有无线能力的设备可以长期通过 SWD 更新，不出现“尚未安装无线”的错误心智；
4. 支持无线的设备可以在首次有线安装后重复无线升级，且升级不会破坏恢复路径；
5. 错误 MCU、容量、硬件适配 ID、布局或协议版本会在擦除前被阻止；
6. 用户只能看到和烧录自己有权限访问且与目标硬件兼容的固件；
7. 每次生成、发布和烧录都能追溯到用户、工作区、源身份、运行时版本、制品摘要和最终结果；
8. 第二种真实硬件接入时不复制工作台主流程，也不要求用户切换到外部烧录工具才能完成闭环。
